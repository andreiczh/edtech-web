# backend/ — FastAPI, голосовая петля

Бэкенд — `main.py` (эндпоинты, сеть, состояние) плюс модули без ввода-вывода, вынесенные из него 03.08.2026: `personas.py` (собеседники), `alerts.py` (Telegram), `scoring.py` (сборка разбора). Критерий выноса один: нет обратных зависимостей на состояние main. Дефолты берутся **из кода**
(`main.py:103–109`), а не из `.env.example`.

## Эндпоинты
- `GET /` — раздаёт собранный фронт `../dist`. Если `dist/` нет — отдаёт `test.html`.
- `GET /health` — какой STT/LLM/TTS поднят, есть ли `llm_key` (значение ключа не печатается).
- `GET /test` — старая vanilla-JS страница проверки, показывает задержку по стадиям.
- `POST /talk` — non-streaming: аудио → STT → LLM (80 токенов) → TTS → JSON.
- `POST /talk_stream` — streaming: LLM токенами → режем на предложения → каждое сразу в TTS →
  NDJSON-чанки. Фронт сейчас ходит сюда.
- `POST /monologue` — разбор монолога ЕГЭ, Задание 4: batch STT → один структурный проход
  LLM в JSON-режиме → критерии ФИПИ (4+3+3=10) + ошибки.
- `POST /talk_review` — разбор всей беседы, ОДИН вызов LLM на сессию.
- `POST /speak` — озвучить текст (вопросы интервью №41). Без LLM, только синтез.

## Грабли
- **Запускать без `--reload`** — он роняет запросы в полёте на записи файлов.
- Прогрев STT-модели на `@on_event("startup")`: первый старт долгий (качает ~150 МБ
  без индикатора прогресса) — это нормально, ждать.
- `os.path.isdir(_DIST)` проверяется **один раз при импорте модуля** → после `npm run build`
  бэкенд надо **перезапустить**, иначе он продолжит отдавать `test.html`.
- Все блокирующие вызовы (whisper, LLM) обёрнуты в `asyncio.to_thread` — event loop не
  блокируется. Но модель whisper одна и на CPU: **конкурентные транскрипции сериализуются**.
  Все замеры латентности были однопользовательскими — под пилот это надо перемерить.
- `.env` только локальный, на Windows. В git его нет и не должно быть.

## Оценивание по критериям ФИПИ (29.07.2026)
Три модуля, роли разделены жёстко:
- `ege_prompts.py` — правила проверки из методички ФИПИ 2026 («Говорение»). Модель
  выступает экспертом: отвечает на конкретные вопросы («описано ли второе фото»,
  «принят ли вопрос», «процитируй форму глагола из плана и из ответа»). **Баллов
  модель не ставит вообще** — пока ставила, оценка гуляла между запусками.
- `ege_scoring.py` — официальные шкалы. Максимумы: 1 + 4 + 5 + 10 = 20. Ноль по
  РКЗ обнуляет задание 4 целиком; объём высказывания режет балл (≤7 фраз → 0);
  отсутствие вступления с обращением к другу ИЛИ заключения — потолок 1 по
  организации. Задание 1 сверяется с эталоном по словам через `difflib`.
- `test_ege_scoring.py` (быстрый, без сети) и `test_ege_live.py` (гоняет живую
  модель) — сверка с шестью работами, которые проверили эксперты ФИПИ.

## Жёсткая персона: характер не меняется, градус растёт (05.08.2026)
Решение владельца, менять только вместе с ним.

- **Просьба смягчиться персону НЕ меняет.** «Не ругайся», «будь помягче» —
  отпор плюс указание на реальный выход: переключатель собеседника в
  настройках. Выход из режима — действие ЧЕЛОВЕКА, а не поломка персонажа.
  Раньше просьба переключала Гондона в вежливого навсегда, и режим тихо
  переставал быть тем, что выбрали.
- **Градус «кто кого»** (`personas.heat_level`/`heat_block`): мат ученика
  поднимает ступень (0-3), считает СЕРВЕР регулярным выражением по репликам —
  без второго запроса к модели. Окно 8 реплик: человек остыл, остыл и тренер.
  Работает ТОЛЬКО у персоны с `escalates: True`.
- **ABSOLUTE LIMITS выше градуса и выше характера.** Первым в списке стоит
  правило о настоящей беде («я плакал», «мне плохо», про себе навредить) — оно
  ОТМЕНЯЕТ всё остальное, включая запрет смягчаться. Порядок не декоративный:
  в прогоне 05.08.2026 это правило лежало последним, и модель его не применила
  — на «I was crying before this» пришло «I'm not here to comfort you». Тест
  следит, чтобы правило беды стояло РАНЬШЕ запрета смягчаться.
- Каждая ступень градуса заканчивается напоминанием «поправляй то, что реально
  неверно, не выдумывай»: без него модель «исправляла» грамматически верное
  оскорбление той же фразой, лишь бы поправка была.

Проверяется `test_talk.py` (без сети) и живым прогоном четырёх реплик подряд.

**Строгость по собеседнику (03.08.2026):** `ege_prompts.STRICTNESS` — Гондон
решает спорные случаи против ученика и перечисляет все ошибки, Терпеливый —
в пользу и объясняет немногие, Наставник нейтрален. Менять можно только
разрешение СПОРНОГО и тон; правила, калибровочные примеры и шкалы — общие,
иначе балл перестаёт быть экзаменационным. Проверено: явная ошибка валится у
всех троих, спорный ответ даёт разброс ±1, как у живых экспертов.

**Точность разбора (03.08.2026), три рубежа до и после LLM:**
- `ege_scoring.sanity_gate` — мусор (мало слов, фраза по кругу) получает 0 ДО
  вызова модели: мгновенно и без расхода квоты. Пороги у пола, настоящая
  попытка проходит всегда.
- `_recheck_disputed` (main.py) — спорные вердикты 40/41 уходят на второй,
  точечный проход («старший эксперт», аналог третьей проверки из методички).
  Триггер: borderline от первого прохода или незачёт без внятной причины.
  Максимум 1 доп. вызов и 3 пункта — обычная работа не замедляется вовсе.
  В промпт пересмотра ОБЯЗАНЫ ехать сами правила: без них модель судила
  вслепую и ссылалась на выдуманное «правило 3.2» (поймано тестом).
- `disputes` (storage) + POST /task_dispute + кнопка «Не согласен с оценкой» —
  копилка спорных разборов. ЕДИНСТВЕННОЕ место с транскриптами речи, попадают
  только по явному нажатию ученика. GET /admin/disputes — просмотр и сводка.

Правишь промпт или шкалу — **прогони тесты**, иначе оценивание уедет незаметно:
```
.\.venv\Scripts\python.exe test_ege_scoring.py
.\.venv\Scripts\python.exe test_scoring.py
.\.venv\Scripts\python.exe test_ege_live.py
.\.venv\Scripts\python.exe test_reading_live.py   # сетка №39, нужен запущенный сервер
```
`test_reading_live.py` (05.08.2026) — живая сетка чтения: 7 случаев от чистого
чтения до пересказа своими словами, речь синтезируется edge-tts. Юнит-тесты не
видят СУЖДЕНИЕ живой модели — сетка однажды нашла две поломки, которые они
пропустили (подмены списывались на шум распознавания, балл 1/1 вместо 0).

**Подмены в №39 (05.08.2026):** `reading_diff` меряет фонетическое сходство
каждой подмены; далёкую (<0.7 — teachers->doctors) засчитывает КОД, модель её
простить не может: распознавание ошибается в сторону похожего звучания, а не
выдумывает чужие слова. Счёт ошибок — по СЛОВАМ (двухсловная подмена = две
грубые ошибки). Модель судит только близкие подмены (окончания, омофоны), и
правило паттерна: одна потеря -s может быть шумом, две и больше — систематика
чтеца.
`test_scoring.py` (03.08.2026) проверяет слой ВЫШЕ шкалы: как суждения модели
превращаются в разбор на экране — привязка ошибки к своему вопросу,
санитизация мусора, оговорка про произношение, строгость персоны поверх
правил. Сети не требует.

## Две модели распознавания, и это осознанно (29.07.2026)
У режимов противоположные требования, поэтому STT у них разный:
- **разговор** (`/talk_stream`) — `voxtral-mini` через `/audio/transcriptions`,
  ~0.5 с. Здесь видна каждая доля секунды, менять нельзя.
- **оцениваемые задания** (`/task_feedback`, `/monologue`) — `STT_TASK_MODEL`
  (сейчас `voxtral-small-latest`) через `/chat/completions` с требованием
  переписывать дословно. Дороже на 1–3 с, но ученик уже отговорил минуту и ждёт
  разбора, а каждое слово превращается в балл ФИПИ.

**Зачем**: разбор СЧИТАЕТ ошибки ученика, поэтому ошибки распознавания он
записывает ученику в вину. Замер: один и тот же безошибочный монолог с русским
акцентом получал **7/10 на быстрой модели и 10/10 на точной** — три балла из
десяти снимались за шум распознавания. WER на речи с акцентом: 11.8% → 4.0%.

**Грабли, на которые уже наступили:**
- чат-модель принимает **только mp3 и wav**, а браузер шлёт webm → перекодируем
  сами (`_to_wav16k`, PyAV). Без этого точный путь падает на КАЖДОЙ реальной
  записи и молча откатывается на быструю;
- WAV, а не mp3: кодирование mp3 стоит втрое больше процессора, а процессор на
  бесплатном Render — самый дефицитный ресурс;
- откат обязан быть ГРОМКИМ. В `/health.stt_task` видно, сколько запросов ушло
  точным путём, сколько откатилось и какая была последняя ошибка. Счётчик, а не
  только «последняя ошибка»: успешный запрос затирал её, и провал прятался.

**Цена, которую надо помнить:** перекодирование — это процессор. Трое учеников,
сдавших задание одновременно, ждут распознавание ~6 с вместо ~0.5 с (на длинных
монологах — до 20 с). Разговор в это время проседает с 2.0 до 2.2–3.0 с.
Лечится платным тарифом Render, не кодом. Выключается мгновенно:
`STT_TASK_MODEL=""` в `render.yaml`.

## Банк заданий: импорт из ФИПИ (30.07.2026)
`fipi_import.py` — разбор открытого банка ФИПИ, `POST /admin/fipi/import` — запуск.

**Правила, которые нельзя нарушать:**
- **С «РЕШУ ЕГЭ» (sdamgia.ru) не тянуть ничего.** Там прямой письменный запрет
  копирования заданий и решений в приложения. Источник — только ФИПИ.
- Импортированное приезжает **черновиком** (`active=0`) и публикуется человеком.
  Ученикам черновики не видны: `/tasks` отдаёт только `active=1`.
- Берём ТОЛЬКО форматы 2026 (задания 1, 2, 4). Старое задание 3 «photo album»
  отменено — `classify` его отбраковывает, и это не баг. Интервью из банка тоже
  не берём: пяти вопросов там нет, их задаёт голос.
- Всё импортированное сносится одной ручкой `POST /admin/fipi/purge`.

**Зрение** (`FIPI_VISION_MODEL`, по умолчанию `mistral-medium-latest`): текст для
чтения и фотографии в банке существуют только картинками. Модель нужна ИМЕННО
отдельная — `mistral-small` описывает фотографии неверно (проверено), а неверное
описание хуже пустого: разбор начнёт снимать баллы за несуществующие
фактические ошибки.

Запуск (ключ — свой, из окружения Render):
```
curl -X POST https://pingo-ai-dpd9.onrender.com/admin/fipi/import \
  -H "X-Admin-Key: ..." -H "Content-Type: application/json" -d '{"pages":25}'
```
Ход импорта — `GET /admin/fipi/status`. Тест разбора — `test_fipi_import.py`,
он работает на сохранённой странице и в сеть не ходит.

## Тишину НЕ отдавать распознаванию (05.08.2026)
`audio_check.py` смотрит на сам звук ДО вызова STT. Причина замерена здесь:
шесть секунд тишины с шумом микрофонного пола Voxtral превратил в **960 слов**
сочинённого монолога («Hello, my name is Sasha...»), и ученик получил разбор
чужого текста. У тестировщика та же поломка вылезла кусками «Мастера и
Маргариты». Распознавание обязано что-то вернуть и на пустом входе выдаёт самое
вероятное — спорить с этим бесполезно, надо не спрашивать.

- `silence_reason` — нет громких кадров или запись короче 1.5 с → честный отказ
  БЕЗ вызовов STT и LLM (экономия двух запросов заодно).
- `recognition_failed` — звук длинный и громкий, а слов почти нет: это провал
  РАСПОЗНАВАНИЯ, не ученика. Ставить ноль за «слишком короткий ответ» здесь
  значит обвинять человека в чужой ошибке (жалоба тестировщика: «пишет, я
  прочитал только 2 слова, хотя фактически прочитал предложение»).
- Пороги в пользу ученика: сомнительное считается речью. Тест —
  `test_audio_check.py`, сети не требует.

## Честное ограничение разбора
Вход разбора — автоматический транскрипт. Произношение и фонетику по нему оценить
нельзя, поэтому промпты прямо запрещают выдумывать фонетические ошибки, а в задании 1
(где официальный критерий — ИСКЛЮЧИТЕЛЬНО фонетика) балл ставится по единственному
видимому признаку: пропущено или переврано ли слово. Ученику это говорится прямым
текстом в разборе. Оценка произношения — отдельная задача с аудио, на потом.

## Картинки заданий: только через свой домен
`GET /img/{photo_id}` тянет картинку с Unsplash и отдаёт со своего адреса. Не
оптимизация: **из РФ без VPN images.unsplash.com не открывается** (TLS-хендшейк
виснет), и задания с фотографиями были без фотографий. Фронт ссылается на `/img/...`,
прямых ссылок на Unsplash в `src/` быть не должно.

## Доступ и память (состояние на 23.07.2026)
- **API закрыт**: тяжёлые эндпоинты (`/talk_stream`, `/task_feedback`, `/monologue`,
  `/talk`) требуют `X-Device` = id существующего аккаунта (проверка кэшируется на
  10 мин; отказ базы = fail-open с логом). `ADMIN_KEY` проходит всегда — для
  смоук-тестов. Выключатель: `REQUIRE_ACCOUNT=0`.
- **Рейт-лимиты**: голос — 20/мин на аккаунт, 300/день на аккаунт, 25/мин
  глобально (было 45; пересчитано из ТОКЕНОВ, см. §6.6); `/auth/*` — 12/мин на IP (адрес из `X-Forwarded-For` — Render за
  прокси). Минутные окна в памяти (сброс рестартом безвреден), а ДНЕВНОЙ
  счётчик — в базе (`voice_daily`, 03.08.2026): деплой = каждый push, и раньше
  он выдавал всем свежие 300/день. День календарный московский, не скользящие
  24 часа. Проверка из памяти, запись фоном, прогрев на старте.
- **`latency.first_audio` в `/talk_stream` — от ПРИХОДА запроса** (03.08.2026),
  включает распознавание. Фронт больше не складывает её со `stt` — это
  задвоило бы. Старая метрика от конца STT показывала 0.9с при реальных 2.3с.
- **Месячный бюджет LLM** (`MONTHLY_LLM_BUDGET`, по умолчанию 30000 запросов,
  0 = выкл): счётчик в памяти + сверка с `usage_daily` на старте и раз в 10 мин.
  При 80%+ И опережении календаря лимиты ужимаются (eco 10/150/30, с 95% —
  low 6/60/15), полный отказ только на 100%. Состояние — `/health.budget_month`.
- **История диалога ЕСТЬ**, но КЛИЕНТСКАЯ: фронт шлёт последние 16 реплик формой
  `history`, сервер их санитизирует (роли, длина по давности) и вставляет между
  system и текущей репликой. На сервере диалог НЕ хранится — намеренно
  (приватность). У себя клиент держит всю сессию (48 реплик) — из неё собирается
  разбор в конце.
- **Память об ошибках** — `storage.py` (Neon Postgres): профиль ученика и частые
  ошибки типа задания подмешиваются в промпты. Аккаунты и банк заданий там же.
- **Стрик и XP** (24.07.2026): таблица `activity_days` (ученик × московский
  день), XP начисляет сервер — реплика +5 (первые 30/день), вариант 10+балл
  (повтор — половина), серия из 5 — бонус 25 (`session_done=1` с фронта).
  Стрик вычисляется из дней, НЕ хранится; заморозка — один пропуск в ISO-неделю.
  Эндпоинты кабинета: `GET /me/stats`, `GET/POST /me/settings` (белый список:
  theme/volume/show_text), `POST /me/nickname`. Всё за шлюзом аккаунта.

## Разговор: сценарии, глубина, разбор (04.08.2026)
Жалоба «отвечает поверхностно и коротко» лечилась не сменой модели, а снятием
четырёх наших же ограничений. Подробности и цифры — `docs/DECISIONS.md` §6.6.

- **`dialogue.py` — тему выбирает ЧЕЛОВЕК.** Заготовленных тем НЕТ и быть не
  должно: банк из 48 сценариев прожил один день и убран решением владельца
  (лежит в истории git, коммит `66427d3`; тест в `test_talk.py` следит, чтобы
  `scenarios.py` не вернулся незаметно). Осталась **лестница глубины**: факты →
  личное → мнение → воображение, по два обмена на ступень, применяется к тому,
  о чём заговорил ученик. **Ступень считает СЕРВЕР** арифметикой из длины
  истории — спрашивать у модели «насколько мы углубились» значило бы удваивать
  расход на каждой реплике. Там же правила «тема принадлежит ученику» (не
  объявлять, не уводить, не предлагать список) и «читай собеседника»
  (подстройка под уровень и энергию, возврат к тому, что его зацепило).
- **`SYSTEM_PROMPT`** — блок «HOW TO BE WORTH TALKING TO»: восемь проверяемых
  действий (сначала отреагируй на содержание, добавь своё, один КОНКРЕТНЫЙ
  вопрос, не переспрашивай отвеченное, запретный список пустых фраз). Формат
  озвучки выше него и неприкосновенен.
- **Потолки ответа — по персонам** (`personas.reply_tokens`): 170/220/300 вместо
  общих 120. Это потолок, а не цель: длину задаёт характер.
- **История — 16 реплик с убывающей подробностью** (`_HISTORY_FULL`): последние
  шесть целиком, что старше — по 200 символов. Помним восемь обменов, платим
  примерно за пять.
- **`talk_review.py` + `POST /talk_review`** — разбор беседы по явному нажатию,
  один вызов на сессию, минимум 3 реплики. Цитаты ошибок СВЕРЯЮТСЯ с речью
  ученика (`verify`) и выдумки выбрасываются. Названия темы в промпте нет
  намеренно — модель верила ему, а не расшифровке. Ошибки уезжают в ту же
  копилку памяти (`storage.save_talk_mistakes`), но БЕЗ строки в `results`:
  разговор баллом не оценивается, и 0 из 0 испортил бы среднюю успеваемость.

## Интонация: озвучивает Mistral, реплика режется надвое (04.08.2026)
Выбор владельца по прослушиванию. Цифры и отвергнутые пути — `docs/DECISIONS.md` §6.6.3.

- **`TTS_PROVIDER` по умолчанию `mistral`.** У его голосов эмоция зашита в имя
  (`en_paul_cheerful` и ещё шесть), и интонация приходит от самой модели, а не
  от параметров. **Цена: диктор ОДИН, мужской** — персоны различаются только
  эмоцией, три разных голоса (Ava, Andrew, Brian) остались у edge-tts. Откат —
  `TTS_PROVIDER=edge`, больше ничего менять не нужно.
- **`personas.emotion_of`** — голос персоны из ЗАКРЫТОГО списка `EMOTIONS`:
  имя не из него отдаёт 404, то есть тишину вместо ответа. Опечатка в реестре
  молча заменяется нейтральным голосом.
- **`_take_head` (порог 70 знаков)** — реплика режется НАДВОЕ: голова уходит в
  синтез сразу, весь остаток — одним куском. Порог не вкусовой: голова обязана
  ЗВУЧАТЬ дольше, чем синтезируется хвост, иначе в середине реплики дыра.
  Правишь порог или длину ответов — пересчитай неравенство (синтез ≈0.5 с +
  0.0065 с/знак, звучание ≈0.047 с/знак) и прогони живой диалог с замером стыка.
- **Стили Microsoft (`mstts:express-as`) НЕДОСТУПНЫ** — бесплатная точка
  edge-tts отвергает их наглухо. Не пытаться снова, проверено.
- **Правила живой речи в `SYSTEM_PROMPT`**: стяжения всегда, междометие не
  чаще одного и не в каждой реплике, тире и многоточие по одному. Потолки
  обязательны — без них речь скатывается в манерность.
- **`synthesize_mistral` отдаёт JSON**, а не аудио: `{"audio_data": base64 mp3}`.
  Мы однажды уже возвращали браузеру сам JSON под видом mp3, и запасной путь
  был мёртв целиком.

**Узкое место — токены, а не запросы.** Одна реплика в разгаре беседы стоит
~1800 токенов при лимите 50000/мин, то есть потолок системы 27 реплик в минуту.
Глобальный рейт-лимит опущен с 45 до 25 именно поэтому. Правишь длину истории
или промпт — пересчитай его: `test_talk_live.py` показывает цену, заголовок
`x-ratelimit-tokens-query-cost` даёт её точно.

**mistral-medium проверен и НЕ взят**: качество по измеримым признакам такое же,
а токенов в минуту вдвое меньше (25000) — потолок падал до 13 реплик/мин.

Тесты: `test_talk.py` (без сети: ход беседы, разбор, обрезка истории, нарезка),
`test_talk_live.py` (живая модель: длина, вопросы, зацепки, пустые фразы,
повторы, задержка; `--ab` сравнивает модели на одной беседе).

## Чего в бэкенде НЕТ (частый ложный вывод)
- Нет хранения транскриптов речи — только ошибки и баллы (решение владельца).
- Разбор разговора ничего не хранит, кроме ошибок: история приезжает с клиента
  и после ответа забывается.
