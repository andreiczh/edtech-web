# Как подключиться к разработке Pingo AI

Для второго разработчика (сейчас — тестировщика, который хочет править код сам).
Инструкция полная: от пустого компьютера до своего коммита в проде.

**Прочитай сначала `CLAUDE.md` в корне** — там устройство проекта и решения,
которые уже приняты и переспоренны быть не могут без веской причины. Здесь —
только доступы и запуск.

| Что | Адрес |

## 2. Доступы: что нужно, а что НЕ нужно

Полный доступ ко всему выглядит удобнее, но у нас он означает конкретные риски.
Ниже — минимум, при котором можно менять ЛЮБОЙ код и запускать всё целиком.

### Нужно

**Приглашение в репозиторий.** Владелец: GitHub → Settings → Collaborators →
Add people → роль **Write**. Приглашение придёт на почту.

**СВОЙ ключ Mistral.** Не владельца, свой:
1. https://console.mistral.ai → зарегистрироваться (карта не нужна);
2. API Keys → Create new key;
3. положить в `backend/.env` (см. шаг 4).

Почему свой, а не общий: ключ один на весь продукт, и его лимиты — это ёмкость
всего сервиса (50 запросов и 50000 токенов в минуту на всех). Отладка чужим
ключом отбирает эту ёмкость у живых учеников, а сам ключ расползается по двум
машинам. Свой ключ бесплатен и ничего этого не делает.

### НЕ нужно для работы над кодом

**ADMIN_KEY от прода.** За ним лежит очередь жалоб, а в ней — расшифровки речи
учеников и их скриншоты. Ученики несовершеннолетние, и это ровно те данные,
которые не раздают «на всякий случай». Для локальной разработки задай в своём
`.env` любой свой `ADMIN_KEY` — админка на своей машине откроется по нему.

**DATABASE_URL от Neon.** Это боевая база целиком. Локально она не нужна вообще:
без переменной проект сам поднимает SQLite-файл `backend/pingo.db`.

**TELEGRAM_BOT_TOKEN.** Алерты нужны только проду.

Если однажды понадобится посмотреть настоящую очередь жалоб — попроси владельца
открыть админку и показать экран, а не пересылать ключ.

## 3. Что поставить

- **Python 3.11** (именно 3.11: под него собран `.venv` и проверены колёса
  `faster-whisper`) — https://www.python.org/downloads/
- **Node.js 20+** — https://nodejs.org
- **Git** — https://git-scm.com

Windows, PowerShell. На Mac/Linux всё то же, кроме `.ps1`-скриптов.

## 4. Запуск с нуля

```powershell
cd C:\Users\<ты>
git clone https://github.com/andreiczh/edtech-web.git edtech-copilot-web
cd edtech-copilot-web
copy backend\.env.example backend\.env
notepad backend\.env
```

В `.env` подставь:

```
LLM_API_KEY=<твой ключ Mistral>
ADMIN_KEY=<любая своя строка, для локальной админки>
```

Остальное в шаблоне уже настроено. Дальше один раз:

```powershell
powershell -ExecutionPolicy Bypass -File backend\run.ps1
```

Скрипт сам подтянет зависимости, соберёт фронт и поднимет сервер на
http://localhost:8000. Первый запуск дольше: ставятся пакеты.

Дальше каждый раз — та же одна команда.

## 5. Правила, которые здесь не вкусовые

Каждое из них выстрадано поломкой. Нарушишь — сломаешь не себе.

**`npm install` ЗАПРЕЩЁН.** Только `npm.cmd ci`. `install` переписывает
`package-lock.json`, выкидывая оттуда бинарники под чужую платформу, и после
этого `git pull` падает у второго человека.

**`.ps1` — только ASCII.** Windows PowerShell 5.1 читает их как CP1251:
кириллица и длинные тире ломают парсер целиком.

**После правки фронта — пересобрать И перезапустить сервер.** Бэкенд решает,
раздавать ли `dist/`, один раз при старте.

**Ветка одна — `main`, feature-веток нет.** Коммить и пушить сразу после
правки, не «потом»: `run.ps1` начинается с `git pull`, и незакоммиченные правки
ломают запуск у второго.

**Без явного «да» владельца НИКОГДА:** `git push --force`, `git reset --hard`,
`git checkout -- .`, `git clean -fd`, `git rebase` (кроме `--abort`).

**`.env` не коммитить.** Он в `.gitignore`, но проверяй `git status` перед
коммитом. Ключи не отправлять в переписку и не вставлять в вывод команд.

## 6. Прогнать тесты перед пушем

Каждый push уезжает в прод, ревью нет — тесты и есть ревью.

```powershell
cd C:\Users\<ты>\edtech-copilot-web
npm.cmd run check
```

Это типы, фронт-тесты и сборка. Дальше бэкенд:

```powershell
cd C:\Users\<ты>\edtech-copilot-web\backend
.\.venv\Scripts\python.exe test_ege_scoring.py
.\.venv\Scripts\python.exe test_scoring.py
.\.venv\Scripts\python.exe test_disputes.py
.\.venv\Scripts\python.exe test_talk.py
.\.venv\Scripts\python.exe test_audio_check.py
.\.venv\Scripts\python.exe test_delivery.py
```

Всё это без сети и без ключа. Тесты, которым нужен ключ и запущенный сервер
(живые сетки, они тратят квоту):

```powershell
.\.venv\Scripts\python.exe test_reading_live.py     # задание 39, ждёт сервер на :8000
.\.venv\Scripts\python.exe test_ege_live.py         # сверка с оценками экспертов ФИПИ
.\.venv\Scripts\python.exe test_talk_live.py        # качество разговора
.\.venv\Scripts\python.exe bench_talk.py            # скорость по этапам
```

## 7. Как здесь принято проверять работу

Правило проекта: **«собралось» не считается за «работает».** Дважды фичи,
написанные и «проверенные» сборкой, оказывались мёртвыми на живом запросе.

Микрофон для проверки не нужен: речь синтезируется `edge-tts` и уходит в
эндпоинт ровно так же, как из браузера — примеры в `test_reading_live.py` и
`bench_talk.py`.

Если правка меняет оценивание — прогони живую сетку ДО и ПОСЛЕ и сравни. Метрика
шумная: один прогон ничего не доказывает, судить только по нескольким.
