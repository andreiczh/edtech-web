# База заданий + память об ошибках («RAG») — конструкция и план интеграции

Запрос: (1) выгружать новые задания в пару кликов в едином интерфейсе;
(2) копить базу частых ошибок — общих по всем ученикам и личных по каждому, —
чтобы LLM обращалась к ним и держала контекст о человеке; (3) не просадить
скорость ответа.

## Главное архитектурное решение: это не классический RAG

Классический RAG (эмбеддинги + векторный поиск на каждый запрос) здесь не нужен
и вреден для скорости. Ошибки учеников — короткие структурированные записи с
готовыми категориями (грамматика/лексика/логика), а заданий — десятки, не
миллионы. Для такого масштаба **структурированная выборка из обычной БД бьёт
векторный поиск** и по качеству, и по скорости.

Скорость защищается одним правилом: **в горячем пути запроса нет ни одного
лишнего вызова LLM и ни одного векторного поиска.** Всё дорогое считается
ЗАРАНЕЕ и асинхронно; во время ответа — один SELECT (5–20 мс) и +300–700
токенов контекста в промпт. Замеренная цена такой добавки — доли секунды.

## Где хранить

**Neon Postgres (free tier)** — без карты, 0.5 ГБ, serverless.

Почему не SQLite на Render: у бесплатного Render **диск эфемерный** — база
стёрлась бы при каждом деплое и перезапуске. Почему не Supabase: тоже можно,
но он за Cloudflare; для сервер-серверных запросов из Франкфурта это не риск,
однако Neon проще (одна строка DSN). Локально для разработки — тот же Postgres
Neon (одна база, меньше расхождений) либо SQLite с тем же SQL через слой.

## Схема данных (5 таблиц)

```sql
users      (id uuid, created_at, note text)            -- анонимный id устройства
tasks      (id, kind, brief, payload jsonb, active bool, created_at)
sessions   (id, user_id, task_id, variant_no, started_at, score int, max int,
            duration_sec int)
mistakes   (id, session_id, user_id, kind, cat text,   -- gram|lex|logic|reading
            quote text, correction text, explanation text, created_at)
digests    (scope text,        -- 'user:<uuid>' | 'global:<kind>'
            text text,         -- готовая выжимка для промпта, <=500 токенов
            updated_at)
```

Идентичность до появления авторизации: анонимный UUID в localStorage браузера,
уходит заголовком `X-Device`. Честное ограничение: сменил браузер — новый
«ученик». При появлении аккаунтов UUID привязывается к аккаунту, история
сохраняется.

Приватность: по умолчанию храним ТОЛЬКО ошибки и баллы, не полные транскрипты.
Ученики — несовершеннолетние, полные записи речи — отдельное решение с
отдельным согласием.

## Поток данных

### Запись (после каждого ответа, вне горячего пути)
`/task_feedback` уже возвращает разбор. Добавляется одно: после отправки ответа
клиенту сервер кладёт сессию и ошибки в БД (`asyncio.create_task` — ученик
ничего не ждёт). Упала запись в БД — ответ ученику всё равно ушёл.

### Выжимки (то, что видит LLM)
Два вида готовых текстов в `digests`:

- **`user:<id>`** — «профиль ошибок ученика»: топ-5 повторяющихся категорий с
  примерами. Пересчитывается ПОСЛЕ сессии, фоново, дешёвым вызовом LLM
  (mistral-small, ~200 токенов на выходе). Триггер: закончилась сессия.
- **`global:<kind>`** — «частые ошибки всех учеников в этом типе задания».
  Пересчитывается по расписанию (раз в сутки) или каждые N новых сессий,
  простым SQL (GROUP BY cat, quote-паттерны) + один вызов LLM для связного
  текста.

### Чтение (горячий путь — единственное место, где важна скорость)
При разборе ответа и в разговоре сервер делает **один** запрос:
`SELECT text FROM digests WHERE scope IN ('user:<id>', 'global:<kind>')`
и вставляет обе выжимки в system-промпт:

```
KNOWN WEAK SPOTS OF THIS STUDENT: <user digest>
COMMON MISTAKES IN THIS TASK TYPE: <global digest>
Pay special attention to these patterns; mention progress if the student
avoided a previously frequent mistake.
```

Бюджет задержки: SELECT по индексированному ключу 5–20 мс, +500 токенов
промпта у Mistral — ~50–150 мс обработки. Итого <0.2 с сверху на разбор,
который и так занимает 2–5 с. В голосовом разговоре выжимка ученика
подгружается один раз при старте сессии и живёт в памяти процесса — там
добавка вообще нулевая.

## База заданий и загрузка «в пару кликов»

Задания переезжают из `src/ege2/tasks.ts` в таблицу `tasks` (payload jsonb —
ровно те же поля, что сейчас у TaskVariant: readText / images / steps / brief).

**Админка — экран `/admin` в самом приложении** (не отдельный сервис):
- вход по `ADMIN_KEY` из переменной окружения (тот же приём, что с ключами);
- форма «добавить вариант»: выбрал тип → появились нужные поля (для 39 —
  текст; для 40 — картинка, 4 пункта; для 41 — 5 вопросов; для 42 — 2 картинки
  и тема) → кнопка «Сохранить». Два клика плюс вставка текста;
- картинки: на первом шаге — вставкой URL; позже — загрузка файла в Neon как
  bytea либо бесплатный бакет (Cloudflare R2 не годится для РФ-раздачи,
  подойдёт хранение в самой БД — картинки задания по 100–300 КБ);
- список существующих вариантов с выключателем `active` — «снять с раздачи»
  без удаления.

Фронт при старте забирает `/tasks` (с кешем в localStorage и ревалидацией по
ETag); встроенный банк из `tasks.ts` остаётся **аварийным фолбэком**, если БД
недоступна — приложение не умирает.

## Состояние (23.07.2026)

**Фаза 1 построена и проверена сквозным тестом**, с двумя отличиями от плана:

- выжимки решено строить **детерминированно из SQL, без LLM**: на этом объёме
  подсчёт категорий с примерами информативнее генеративного пересказа, стоит
  миллисекунды и не может ни соврать, ни упасть по квоте. LLM-пересказ профиля
  вернётся в план, когда данных станет много;
- по решению владельца храним **только ключевую информацию**: категории ошибок,
  пары «как сказал → как надо», баллы. Транскрипты не хранятся вовсе.

Что работает: `backend/storage.py` (SQLite сразу / Postgres по `DATABASE_URL`,
один код), анонимный `X-Device` с фронта, запись ошибок фоном после каждого
разбора, две выжимки (профиль ученика + частые ошибки типа задания), их
подстановка в промпты `/task_feedback` и `/talk_stream` параллельно с STT.
Замерено: добавка памяти к времени ответа — ноль (выборка успевает раньше STT).

**Постоянное хранилище подключено 23.07.2026:** проект Neon `speako` (free tier,
0.5 ГБ, без карты), `DATABASE_URL` живёт в переменных окружения Render.
`/health` отдаёт `"memory": "postgres (Neon)"`. Деплой больше не стирает
накопленное.

Смотреть данные: console.neon.tech → проект speako → **Tables** (таблицы
`students`, `results`, `mistakes`, `digests`) или **SQL Editor**.

Если однажды понадобится поднять всё заново: завести проект в Neon, скопировать
Connection string, положить её в `DATABASE_URL` на Render. Схема создаётся сама
при старте (`ensure_schema`). Без переменной сервер молча падает на SQLite и
продолжает работать — продукт не зависит от наличия базы.

## Состояние фазы 2 (23.07.2026): банк заданий, админка и аккаунты — работают

- **Банк заданий в базе**: таблица `tasks`, `GET /tasks` (публично, только
  активные), фронт подмешивает серверные варианты к встроенным — встроенные
  остаются аварийным минимумом без базы.
- **Админка**: открывается по адресу `/?admin`, требует `ADMIN_KEY` (переменная
  окружения на Render, задать руками в Environment). Выбор раздела (ЕГЭ/ОГЭ/
  другое) и номера → появляются ровно нужные поля → «Сохранить». Текст задания
  собирается из шаблонов сам. Список добавленного с выключателем «в выдаче».
- **Аккаунты**: регистрация по нику (генерация из двух английских слов + Change)
  и паролю, выбор ОГЭ→«soon…»/ЕГЭ/другое, карточка «запиши данные — восстановления
  нет». id аккаунта = идентичность памяти: история и прогресс следуют за
  человеком между устройствами (`GET /progress` доливает решённые варианты).
- **Найденные тестом грабли** записаны в код: брошенное после ошибки соединение
  SQLite держало блокировку файла и убивало все последующие записи — теперь
  соединение бросается только с rollback+close (`storage._drop_connection`).

## План интеграции по фазам

| Фаза | Что | Объём | Риск для скорости |
|---|---|---|---|
| 1 | Neon + таблицы + запись сессий/ошибок из `/task_feedback` (fire-and-forget), `X-Device` на фронте | ~день | нулевой (вне горячего пути) |
| 2 | Таблица tasks + `/tasks` API + фолбэк на встроенный банк + экран `/admin` с ADMIN_KEY | ~день | нулевой (загрузка при старте) |
| 3 | digests: пересчёт профиля после сессии + глобальный по расписанию; вставка выжимок в промпты разбора и разговора | ~полдня | +1 SELECT и +500 токенов, <0.2 с — замерить до/после |
| 4 (позже) | Настоящий векторный слой (pgvector на Neon + Mistral embeddings), когда заданий станут сотни: подбор похожих заданий, поиск по формулировкам | 1–2 дня | нулевой для ответа (поиск заданий — не горячий путь) |

Порядок именно такой: фаза 1 сразу начинает копить данные (они ценнее кода —
чем раньше пишем, тем богаче база к моменту фазы 3), фаза 2 снимает ручную
правку tasks.ts, фаза 3 включает «память» в промпты.

## Что НЕ делаем и почему

- **Эмбеддинги на каждый запрос** — дорого по времени и не нужно на этом
  масштабе; появятся в фазе 4 и только вне горячего пути.
- **Полные транскрипты по умолчанию** — приватность несовершеннолетних.
- **Отдельный админ-сервис** — второй деплой, второй логин; экран в
  приложении за ADMIN_KEY решает то же в десять раз дешевле.
- **Выжимку в КАЖДУЮ реплику разговора** — грузим раз в сессию, в память.
