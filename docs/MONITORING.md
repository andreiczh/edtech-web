# Мониторинг: как узнать о падении раньше учеников

Две независимые половины. Обе бесплатные, обе настраиваются один раз.

## 1. Внешний пингер (обязательно — сам себя мёртвый сервер не разбудит)

UptimeRobot, бесплатный тариф (50 мониторов, проверка раз в 5 минут).

1. Зарегистрируйся на https://uptimerobot.com (почта + пароль).
2. **Add New Monitor**:
   - Monitor Type: `HTTP(s)`
   - Friendly Name: `Pingo AI`
   - URL: `https://pingo-ai-dpd9.onrender.com/health`
   - Monitoring Interval: `5 minutes`
3. В **Alert Contacts** добавь свою почту (или их Telegram-интеграцию).

Готово: письмо при падении и при восстановлении. Бонус: пинги раз в 5 минут
не дают Render заснуть днём — наш самопинг остаётся страховкой.

## 2. Алерты из самого сервера (Telegram)

Сервер шлёт владельцу СОБЫТИЯ (не поток логов):
- рестарт процесса (= деплой или падение с подъёмом);
- бюджет LLM перешёл в eco / low / empty;
- 5 сбоев STT или LLM за 10 минут (единичные обрывы не алертят);
- edge-tts деградировал на запасной Mistral (пропали голоса персон).

Одна тема — не чаще раза в 30 минут, шторма не будет.

### Настройка (5 минут)

Часть шагов может сделать только человек — их отмечено «ТЫ». Остальное берёт
на себя админка (`/?admin`).

1. **ТЫ:** в Telegram найди **@BotFather** → `/newbot` → имя и username бота.
   Он выдаст **токен** вида `1234567:AA...`. Никому его не показывай.
2. **ТЫ:** Render → Environment → `TELEGRAM_BOT_TOKEN` = этот токен →
   Save (сервис перезапустится сам).
3. **ТЫ:** напиши своему боту любое сообщение — боты не могут писать первыми.
4. **АДМИНКА:** открой `/?admin`, блок «Алерты в Telegram». Сервер сам сходит
   в Telegram своим токеном и покажет твой **chat_id** — выковыривать его из
   сырого JSON руками больше не нужно.
5. **ТЫ:** Render → Environment → `TELEGRAM_CHAT_ID` = это число → Save.
6. **АДМИНКА:** кнопка «Отправить тест». Пришло сообщение — канал работает.
   Не пришло — там же будет написана причина («chat not found» и т. п.).

Без этих переменных сервер просто молчит — ничего не ломается.

## 3. Бэкап базы (Neon free своих бэкапов не делает)

В базе живёт всё: аккаунты, прогресс, банк заданий, копилка жалоб.
Дамп забирается ручкой `/admin/backup` на твой ноут.

**Рабочий скрипт — `backend/backup.py`, НЕ backup.ps1** (16.08.2026).
PowerShell-версия трижды молча исчезала с диска: антивирус 360 Total Security
считает .ps1 с веб-запросом и записью файлов «загрузчиком» и удаляет без
следа в журналах. Python из .venv той же эвристикой не задет. Логика та же.
Пока 360 стоит на машине, добавь папку проекта в его исключения — иначе он
продолжит выкашивать и другие .ps1 (например, run.ps1), а их пропажа ломает
`git pull` при запуске.

1. Задай переменную окружения ОДИН раз (PowerShell от своего пользователя):
   `setx PINGO_ADMIN_KEY "твой-админ-ключ"`
   (запасной путь: скрипт возьмёт PROD_ADMIN_KEY из backend/.env).
2. Проверь руками:
   `C:\Users\Lenovo\edtech-copilot-web\backend\.venv\Scripts\python.exe C:\Users\Lenovo\edtech-copilot-web\backend\backup.py`
   — в `%USERPROFILE%\pingo-backups` появится `pingo-<дата>.json`.
3. Задача «PingoBackup» в планировщике уже перенастроена (16.08.2026): зовёт
   `pythonw.exe backup.py` без окна на экране, каждую ночь в 03:30, работает
   и от батареи, пропуск догоняет при первом пробуждении. Пересоздавать её
   не нужно; если когда-то придётся — действие задачи именно такое.

Скрипт хранит последние 14 дампов и сам удаляет старые. Формат — обычный
JSON по таблицам: восстановление не требует спецсредств.

**Как понять, что бэкап живой.** Задача в планировщике проваливается молча —
никто не смотрит на её код возврата, и дамп, который месяц сохраняет страницу
ошибки вместо базы, выглядит защитой, ею не являясь. Поэтому скрипт:

- пишет КАЖДЫЙ запуск в `%USERPROFILE%\pingo-backupsackup.log` строкой
  вида `OK: pingo-2026-08-04_0330.json (4488 KB) accounts=13 results=47
  mistakes=79 disputes=5 tasks=94` — по числам сразу видно, что внутри база,
  а не заглушка;
- не принимает дамп, пока тот не разберётся как JSON и не окажется непустым:
  неверный ключ отдаёт аккуратную страницу ошибки в тысячу байт, и проверки
  «файл больше 100 байт» для неё мало;
- при провале удаляет огрызок и возвращает код 1, при успехе — 0.

Раз в пару недель загляни в `backup.log`: три строки `FAILED` подряд означают,
что бэкапа нет, сколько бы файлов ни лежало в папке.

Проверено 05.08.2026 на всех трёх путях: неверный ключ, недоступный сервер,
успешный дамп.
